# Стратегия тестирования

## 1. Цели

Тесты должны гарантировать:

- неизменность формулы очков;
- корректность DNF/MISSED;
- атомарность повторного импорта;
- детерминированный лидерборд;
- сохранность истории;
- корректность ручной сетки;
- защиту админских операций;
- визуальное соответствие референсам.

## 2. Уровни

### Unit

Инструменты:

- Vitest для shared/frontend;
- Vitest для NestJS;
- чистые функции домена не зависят от NestJS/Prisma.

Обязательные unit-наборы:

#### Очки

- чётное `P`;
- нечётное `P`;
- `P = 2`;
- первое, второе и третье место;
- последнее очковое место;
- первое неочковое место;
- DNF;
- MISSED;
- посторонний игрок;
- одинаковое время.

#### Среднее

- только COMPLETED;
- COMPLETED + DNF;
- COMPLETED + MISSED;
- все DNF;
- изменение активной версии импорта;
- округление только для отображения, не для внутренней суммы.

#### Лидерборд

- разные очки;
- равные очки и разные средние;
- равные очки и средние;
- одинаковый ник с разными UUID;
- пустой дивизион.

#### Timeline

- нормальная последовательность фаз;
- отсутствующие промежуточные события;
- повторяющиеся события;
- completion без complete event;
- DNF на каждой фазе;
- пустой timeline.

#### Плей-офф

- размеры 4/8/16;
- число раундов и матчей;
- winner не входит в пару;
- равный счёт;
- участник дважды в одном раунде;
- скрытый/видимый матч за третье место;
- ручная коррекция раннего раунда.
- публикация запрещена при пустой позиции первого раунда;
- скрытый матч за третье место не блокирует завершение турнира;
- optimistic locking версий сетки и матча.

## 3. Integration backend

Тесты работают с отдельным PostgreSQL.

Обязательные сценарии:

- создание турнира создаёт три дивизиона;
- старт с одним, двумя и тремя непустыми дивизионами;
- запрет старта, если пусты все дивизионы;
- фиксация и публичная выдача только участвующих дивизионов;
- unique участника в турнире;
- фиксация состава после импорта;
- импорт preview ничего не записывает;
- успешный импорт создаёт активную версию;
- reimport меняет active version;
- неудачный reimport не меняет публичные данные;
- reimport пересчитывает все агрегаты;
- duplicate `rankedMatchId`;
- optimistic locking;
- завершённый турнир отклоняет обычную запись;
- correction завершённого требует reason + confirm;
- аудит создаётся в той же транзакции;
- final checklist блокирует завершение при pending import или незавершённой
  опубликованной сетке;
- сервер повторно проверяет readiness при команде `COMPLETED`;
- audit list применяет фильтры и cursor pagination;
- audit details возвращает снимки `before`/`after`;
- публикация неполной сетки запрещена.
- публичный endpoint выдаёт только опубликованную сетку.

Ranked API подменяется mock server с payload fixtures.

## 4. Contract tests

- OpenAPI генерируется на каждом CI run.
- Schema diff не допускает незаявленных breaking changes.
- Frontend contracts проверяются против OpenAPI.
- Fixtures соответствуют локальному `openapi.yaml` Ranked API.
- Adapter-тесты отдельно проверяют отклонение неожиданных внешних форматов.

## 5. Frontend component tests

Инструменты:

- React Testing Library;
- Vitest;
- axe для accessibility smoke checks.

Проверки:

- переключатель турниров;
- вкладки дивизионов;
- qualification/playoff toggle;
- лидерборд;
- карточка участника;
- окно матча;
- drawer;
- формы login/турнира/регистраций/import preview;
- редактор сетки;
- финальный checklist завершения;
- журнал аудита, фильтры и diff;
- ошибки 409/422/502.

## 6. E2E

Playwright запускается против собранных frontend/backend и тестовой БД.

Команды:

```powershell
pnpm test:e2e
pnpm test:e2e:ui
```

Обычный запуск сам собирает и временно поднимает backend и frontend preview.
Публичные smoke-тесты выполняются в desktop и mobile Chromium. Административные
сценарии требуют `E2E_ADMIN_USERNAME` и `E2E_ADMIN_PASSWORD`; сценарии с записью
дополнительно требуют `E2E_ALLOW_MUTATIONS=true` и поэтому включаются только на
изолированной CI/тестовой БД.

Критические потоки:

1. Администратор входит.
2. Создаёт турнир и обложку.
3. Добавляет участников.
4. Публикует и запускает квалификацию.
5. Импортирует матч.
6. Проверяет публичный лидерборд.
7. Повторно импортирует изменённый fixture.
8. Создаёт и публикует сетку.
9. Заполняет счёт и проверяет автоматическое продвижение игрока.
10. Завершает турнир.
11. Проверяет блокировку обычного редактирования.
12. Выполняет корректирующий импорт с причиной и подтверждением.
13. Проверяет обновлённую публичную историю и diff в журнале аудита.

## 7. Visual regression

Эталонные viewport:

- 1440 × 900;
- 1280 × 720;
- 768 × 1024;
- 390 × 844;
- 360 × 800.

Снимки:

- квалификация без выбора;
- окно участника;
- окно результата с COMPLETED/DNF/MISSED;
- сетки 4/8/16;
- mobile drawer;
- предстоящий турнир;
- skeleton и ошибки.

Допуск pixel diff задаётся после утверждения первой эталонной реализации.

## 8. Security tests

- brute-force rate limit;
- cookie flags;
- CSRF;
- unauthorized admin endpoints;
- malformed UUID/match ID;
- XSS в описании и никах;
- MIME spoofing;
- oversized upload;
- SSRF попытки через match ID;
- session revocation;
- audit не содержит секретов.

## 9. Performance

Наборы данных:

- 10 турниров;
- 100 участников на дивизион;
- 50 матчей на дивизион;
- 16-player bracket.

Цели:

- публичный leaderboard API p95 < 500 ms;
- публичный match details p95 < 500 ms;
- обычный admin API p95 < 750 ms;
- импорт без учёта внешнего Ranked latency < 2 s;
- frontend LCP публичной страницы < 2.5 s на нормальном мобильном соединении.

Минимальный автоматический performance gate делает 20 запросов к публичному
списку турниров и требует p95 < 500 ms. Полный профиль на максимальном наборе
данных повторяется на staging перед production release.

## 10. Приёмка исправлений

Каждый bug fix включает тест, воспроизводящий проблему. Исключение допускается только для чисто визуального исправления, которое покрывается visual snapshot.

## 11. CI gates

Merge запрещён при ошибке:

- format;
- lint;
- typecheck;
- unit;
- integration;
- OpenAPI validation;
- production build;
- migration check;
- dependency security check с критической уязвимостью.

Workflow `.github/workflows/ci.yml` содержит два обязательных задания:

- quality: frozen install, Prisma generate/`pnpm db:validate`, format, lint, typecheck,
  unit/integration, build и dependency audit;
- e2e: отдельный PostgreSQL, миграции, seed, Chromium и Playwright-сценарии,
  включая административную мутацию.
