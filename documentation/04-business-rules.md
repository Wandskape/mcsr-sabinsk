# Бизнес-правила

## 1. Турнир и статусы

### 1.1 Создание

- Название, описание, даты и лимиты трёх доступных типов дивизионов обязательны до публикации.
- В момент перехода в `QUALIFICATION` участвующими фиксируются только непустые дивизионы.
- Для старта нужен хотя бы один дивизион с зарегистрированными участниками.
- Пустые на момент старта дивизионы не участвуют в турнире, не принимают импорты и не выдаются публично после начала квалификации.
- `startsAt < endsAt`.
- Slug уникален и после первой публикации не меняется штатным интерфейсом.
- Обложка обязательна для перехода в `UPCOMING`.

### 1.2 Переходы

| Из | В | Условия |
|---|---|---|
| DRAFT | UPCOMING | заполнены обязательные поля и обложка |
| UPCOMING | QUALIFICATION | есть хотя бы один непустой дивизион; все непустые дивизионы фиксируются как участвующие |
| QUALIFICATION | PLAYOFF | администратор завершил импорт квалификации |
| PLAYOFF | COMPLETED | опубликованные сетки заполнены либо администратор подтвердил их отсутствие |

Допускается пропустить `PLAYOFF`, если во всём турнире не создано ни одной сетки.

### 1.3 Завершение

- Обычные операции записи после `COMPLETED` запрещены.
- Корректирующий импорт доступен отдельной командой.
- Корректирующая команда требует:
  - повторного ввода `match_id`;
  - текстовой причины не короче 10 символов;
  - флага подтверждения;
  - актуальной версии сущности.

## 2. Регистрации

### 2.1 Проверка Ranked-профиля

1. Администратор вводит ник.
2. Backend вызывает `GET /users/{identifier}`.
3. Успешный ответ даёт UUID и канонический текущий ник.
4. UUID используется для поиска или создания `Participant`.
5. В регистрацию записывается снимок ника.

Если Ranked API недоступен, новая регистрация не создаётся. Администратор получает повторяемую ошибку, а уже сохранённые данные продолжают работать.

### 2.2 Уникальность

- UUID не может быть зарегистрирован дважды в одном турнире.
- Совпадение ников с разными UUID считается конфликтом и требует проверки администратором.
- Перенос между дивизионами до первого импорта разрешён.
- После первого импорта перенос является корректирующей операцией с полным пересчётом.

### 2.3 Фиксация состава

После первого успешно импортированного матча дивизиона состав считается зафиксированным. Это гарантирует однозначный список MISSED для каждого матча.

## 3. Обработка квалификационного матча

### 3.1 Участники

Из `data.players` Ranked API берутся только UUID, зарегистрированные в выбранном дивизионе.

Игнорируются:

- `spectators`;
- игроки из `players`, не зарегистрированные в дивизионе;
- зарегистрированные игроки, выбывшие по итогам предыдущего матча;
- хосты и трансляторы без регистрации.

Зарегистрированный участник считается фактически участвовавшим, если его UUID присутствует в `data.players`.

### 3.2 Статусы результата

#### COMPLETED

Все условия истинны:

- UUID присутствует в `data.players`;
- существует `completion`;
- `completion.time <= division.timeLimitMs`.

#### DNF

UUID присутствует в `data.players` и выполняется одно из условий:

- `completion` отсутствует;
- `completion.time > division.timeLimitMs`.

#### MISSED

UUID зарегистрирован в дивизионе, но отсутствует в `data.players`.

### 3.3 Места

- Места получают только COMPLETED.
- COMPLETED сортируются по `rawTimeMs` по возрастанию.
- При одинаковом времени используется `nicknameSnapshot`, затем Ranked UUID.
- Места нумеруются последовательно с 1.
- DNF и MISSED имеют `placement = null`.

## 4. Формула очков

Ranked API возвращает `completions` как массив фактически завершивших забег,
но не возвращает настроенное максимальное число финишей матча. Поэтому
администратор при preview каждого матча обязательно выбирает
`completionLimit`: 4, 6, 8, 10 или 12. Значение входит в подписанный preview,
сохраняется в матче и в каждой версии импорта.

Пусть `C` — `completionLimit`, а `R` — место финишировавшего участника:

```text
если status != COMPLETED → 0
если R > C               → 0
иначе                     → 24 - 2 × (R - 1)
```

Количество зарегистрированных участников и число фактических финишей не
изменяют шкалу. Если `C = 12`, но завершили только восемь игроков, они получают
24, 22, 20, 18, 16, 14, 12 и 10 очков; остальные получают 0.

Матч, в котором участвовало меньше двух зарегистрированных игроков дивизиона,
отклоняется как некорректный для квалификации.

| Лимит | Очки по местам |
|---:|---|
| 4 | 24, 22, 20, 18 |
| 6 | 24, 22, 20, 18, 16, 14 |
| 8 | 24, 22, 20, 18, 16, 14, 12, 10 |
| 10 | 24, 22, 20, 18, 16, 14, 12, 10, 8, 6 |
| 12 | 24, 22, 20, 18, 16, 14, 12, 10, 8, 6, 4, 2 |

## 5. Среднее время

Для каждой регистрации и каждого импортированного матча дивизиона определяется `effectiveTimeMs`:

```text
COMPLETED → rawTimeMs
DNF       → division.timeLimitMs
MISSED    → division.timeLimitMs
```

Среднее:

```text
averageTimeMs = sum(effectiveTimeMs) / количество импортированных матчей дивизиона
```

Следствия:

- пропуск ухудшает среднее;
- DNF ухудшает среднее;
- каждый активный участник имеет одинаковое число элементов в среднем;
- после выбывания новые матчи больше не входят в среднее участника;
- изменение лимита после первого импорта запрещено без корректирующего пересчёта.

## 6. Лидерборд

Сумма очков:

```text
qualificationPoints = sum(points всех активных результатов)
```

Порядок:

1. `qualificationPoints` по убыванию;
2. `averageTimeMs` по возрастанию;
3. `nicknameSnapshot` через locale-insensitive сравнение;
4. Ranked UUID для полной детерминированности.

Место в таблице является последовательным индексом после сортировки. Совместных мест нет.

### 6.1 Выбывание

Выбывание накопительное. Выбывший участник остаётся в лидерборде, но не
участвует в последующих квалификационных матчах. Если его UUID присутствует в
Ranked-матче, результат игнорируется.

Для `BEGINNER`:

| После матча | Правило |
|---:|---|
| 3 | выбывают все участники с 0 очков |
| 4 | остаётся top-8 |
| 5 | остаётся top-4 |

Для `EXPERIENCED` и `PRO`:

| После матча | Правило |
|---:|---|
| 3 | выбывают все участники с 0 очков |
| 5 | остаётся top-8 |
| 7 | остаётся top-6 |
| 8 | остаётся top-4 |

Граница top-N использует полный порядок лидерборда: очки, среднее время, ник,
Ranked UUID. При reimport состояние выбывания пересчитывается с первого матча.
Участник может вернуться только вследствие исправления исторических результатов.
Если возвращение затрагивает уже импортированные последующие матчи, отсутствие
сохранённого результата считается `MISSED` до повторного импорта такого матча.

Активные участники всегда располагаются выше строки «ВЫБЫЛИ». Выбывшие
сортируются между собой тем же тай-брейком. Выбор администратором сетки
плей-офф на 4, 8 или 16 человек остаётся доступным независимо от текущей границы.

## 7. Победитель квалификационного матча

- Победитель — COMPLETED с `placement = 1`.
- Если никто не завершил матч в лимит, победитель отсутствует.
- В публичном списке показывается «Нет финишировавших».

## 8. Timeline

Для каждого фактически участвовавшего игрока сохраняются:

- финальное или последнее известное время;
- последняя достигнутая фаза;
- нормализованные цветные сегменты.

Основные фазы:

1. Overworld;
2. Nether;
3. Bastion;
4. Fortress;
5. Blind Travel;
6. Stronghold;
7. The End;
8. Finished.

События, не меняющие основную фазу, не создают отдельный сегмент. Исходные timeline-события остаются в raw payload версии импорта.

### 8.1 Тип мира и бастиона

- Из ответа Ranked API сохраняются nullable-поля `data.seedType` и
  `data.bastionType`.
- Тип мира нормализуется к одному из значений: `BURIED_TREASURE`, `SHIPWRECK`,
  `VILLAGE`, `RUINED_PORTAL`, `DESERT_TEMPLE`.
- Тип бастиона нормализуется к одному из значений: `BRIDGE`, `HOUSING`,
  `TREASURE`, `STABLES`.
- Значения хранятся в каждой версии импорта вместе с исходным `rawPayload`.
  Повторный импорт может обновить их только созданием новой версии.
- Исторические импорты заполняются из уже сохранённого `rawPayload`, без новых
  запросов к Ranked API.
- Неизвестное, отсутствующее или новое значение API сохраняется как `null` и
  отображается как «Неизвестно», не блокируя импорт результатов.
- В публичном окне матча под заголовком в одну строку показываются две пары:
  изображение и русское название типа мира, затем изображение и английское
  название типа бастиона.

## 9. Повторный импорт

- Повторный импорт заменяет весь активный набор результатов матча.
- Частичное редактирование одного участника не поддерживается.
- После применения пересчитываются все регистрации дивизиона.
- Если payload совпадает по hash с активным, операция возвращает существующий результат без новой версии.
- При изменении Ranked `match_id` существующего матча используется операция замены с отдельным подтверждением.
- Неудачная версия сохраняет технический статус FAILED, но не становится активной.

## 10. Плей-офф

### 10.1 Размер

Первая версия поддерживает 4, 8 и 16 участников. Размер выбирает администратор при создании сетки.
Сетка создаётся только для участвующего дивизиона во время `QUALIFICATION` или
`PLAYOFF`; число регистраций дивизиона должно быть не меньше выбранного размера.
После создания размер не изменяется.

Число основных матчей:

```text
size - 1
```

Дополнительно может быть один матч за третье место.

### 10.2 Ручное управление

- Backend создаёт пустые позиции раундов и связи для отрисовки.
- При создании сетки backend фиксирует top-N квалификации: очки по убыванию,
  среднее время по возрастанию, затем ник и Ranked UUID.
- В списках первого раунда доступны только эти top-N участников.
- Администратор вручную назначает пары первого раунда.
- Администратор вручную вводит неотрицательный целочисленный счёт.
- Администратор вручную выбирает победителя.
- Backend не выводит победителя из счёта.
- После сохранения победитель автоматически занимает связанную позицию
  следующего раунда.
- Это позволяет отразить техническую победу и нестандартные решения организаторов.

### 10.3 Валидация

- Один участник не может занимать две позиции одного раунда.
- Участник обязан быть зарегистрирован в дивизионе.
- Победитель обязан быть участником матча.
- Завершённый матч имеет обоих участников, оба значения счёта и winner.
- Равный счёт разрешён только для незавершённого матча без winner.
- Исправление победителя раннего раунда автоматически меняет связанную позицию,
  сбрасывает счёт и победителя затронутого следующего матча и каскадно очищает
  устаревшее продвижение.

### 10.4 Матч за третье место

- Создаётся или скрывается флагом `showThirdPlace`.
- Позиция матча хранится всегда, поэтому повторное включение восстанавливает
  ранее введённые данные.
- При скрытии данные не удаляются, но не выдаются публично.
- После завершения полуфиналов их проигравшие назначаются автоматически.

### 10.5 Публикация

- Неопубликованная сетка видна только администратору.
- Публичный переключатель «Плей-офф» появляется при `isPublished = true`.
- Публикация разрешена при заполненных участниках первого раунда.
- Пустые будущие раунды отображаются как ожидающие.

## 11. Ники

- Исторические таблицы показывают `nicknameSnapshot`.
- Ссылка на актуальный Ranked-профиль строится по UUID.
- Обновление текущего ника участника не переписывает автоматически исторические снимки.
- Администратор может явно синхронизировать ник регистрации до завершения турнира.

## 12. Часовой пояс

- Backend принимает и возвращает даты ISO 8601 в UTC.
- Frontend форматирует их в `Europe/Moscow`.
- В интерфейсе явно показывается «МСК», если отображается время события.
