# Безопасность

## 1. Модель угроз

Защищаем:

- административный доступ;
- целостность исторических результатов;
- пароли и сессии;
- PostgreSQL и объектное хранилище;
- приложение от вредоносных внешних payload;
- аудит от незаметного изменения.

Публичные турнирные данные не считаются секретными.

## 2. Учётные записи

- Самостоятельная регистрация отсутствует.
- Первого администратора создаёт CLI-команда.
- Логины уникальны без учёта регистра.
- Минимальная длина пароля — 12 символов.
- Пароль хешируется Argon2id с параметрами, соответствующими ресурсам production.
- Пароль никогда не логируется и не передаётся обратно.
- При изменении пароля все сессии отзываются.

## 3. Защита входа

- Rate limit по IP и логину.
- После 5 неудачных попыток — временная блокировка.
- Сообщение входа не раскрывает, существует ли логин.
- Все входы и блокировки фиксируются.
- Production работает только по HTTPS.

## 4. Сессии

- Случайный токен минимум 256 бит.
- В базе хранится только hash токена.
- Cookie: `HttpOnly`, `Secure`, `SameSite=Strict`, ограниченный path.
- Idle timeout: 8 часов.
- Absolute timeout: 24 часа.
- Logout и деактивация пользователя отзывают сессию.

## 5. CSRF и CORS

- Админские изменяющие запросы требуют CSRF token.
- CORS разрешает только настроенные origin.
- В штатном production frontend и API обслуживаются через один origin.
- `Origin`/`Referer` проверяются для критических операций.

## 6. Валидация

- DTO backend используют whitelist и запрещают неизвестные поля.
- Общие Zod-схемы валидируют client input.
- Backend повторно проверяет все данные независимо от frontend.
- Markdown/HTML от администратора не исполняется; описание выводится как безопасный текст либо проходит allowlist sanitizer.
- Slug, ник, ID, размер файла и MIME имеют явные ограничения.

## 7. Ranked API

- Внешний ответ считается недоверенным.
- Payload проверяется runtime-схемой.
- HTTP redirect отключён либо ограничен разрешённым host.
- Используется фиксированный base URL.
- Пользователь не может передать произвольный URL.
- Private-Key Ranked API не требуется и не хранится.
- Raw payload не попадает в публичный API.

## 8. Загрузка файлов

- Разрешены JPEG, PNG и WebP.
- Максимальный размер исходника — 8 MB.
- Файл проверяется по magic bytes, а не только MIME.
- Изображение декодируется и при необходимости перекодируется.
- SVG не принимается.
- Object key генерируется сервером.
- Публичный URL не позволяет листинг bucket.

## 9. База данных

- Backend использует отдельного пользователя БД с минимальными правами.
- Migration user отделён от runtime user в production.
- PostgreSQL не доступен из публичной сети.
- SQL только параметризованный.
- Production secrets не хранятся в git.
- Backup шифруется и имеет ограниченный доступ.

## 10. Аудит

Аудит append-only на уровне приложения. Изменение/удаление записей через API отсутствует.

Особо важные события:

- коррекция завершённого турнира;
- смена статуса;
- изменение состава после фиксации;
- повторный импорт;
- изменение опубликованной сетки;
- замена обложки;
- смена пароля.

## 11. Заголовки

Минимум:

- Content-Security-Policy;
- Strict-Transport-Security;
- X-Content-Type-Options: nosniff;
- Referrer-Policy;
- Permissions-Policy;
- frame-ancestors через CSP.

CSP разрешает изображения только от собственного object storage и явно перечисленных источников аватаров.

## 12. Зависимости

- Lockfile обязателен.
- CI выполняет dependency audit.
- Обновления security patch применяются приоритетно.
- Неподдерживаемые версии Node.js, NestJS, Astro, React, Prisma и PostgreSQL запрещены.

## 13. Секреты

Production secrets:

- `DATABASE_URL`;
- session signing/encryption secret;
- CSRF secret;
- S3 credentials;
- bootstrap admin password только на момент создания.

Секреты передаются через secret manager или защищённые переменные окружения.

## 14. Реакция на инцидент

1. Отозвать активные сессии.
2. При необходимости деактивировать администратора.
3. Сохранить логи и аудит.
4. Сменить затронутые секреты.
5. Проверить целостность активных импортов и сеток.
6. Восстановить из backup только после определения точки компрометации.
