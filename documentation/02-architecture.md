# Архитектура

## 1. Архитектурный стиль

Первая версия строится как модульный монолит:

```text
Browser
  │
  ├── Astro + React frontend
  │       │
  │       └── REST /api/v1
  │
  └──── NestJS backend
          ├── PostgreSQL через Prisma
          ├── S3-совместимое хранилище
          └── MCSR Ranked API
```

Модульный монолит выбран вместо микросервисов, потому что:

- домен требует транзакций между импортом и пересчётом;
- ожидаемый объём невелик;
- один backend проще разворачивать и наблюдать;
- модули можно разделить позже без преждевременного усложнения.

## 2. Структура монорепозитория

```text
apps/
  frontend/
    src/
      components/
      features/
        tournaments/
        qualification/

        admin/

  backend/
    prisma/
      schema.prisma
      migrations/
      seed.ts
    src/
      modules/
        auth/
        admins/
        tournaments/
        divisions/
        participants/
        qualification/
        ranked/
        playoffs/
        media/
        audit/
      common/
      config/
      main.ts
packages/
  shared/
    src/
      enums/
      contracts/
      schemas/
      utils/
documentation/
```

Каждое приложение имеет собственный `src`. Корневой `src/front` и `src/back` не используется.

Workspace управляется `pnpm` через Corepack. В репозитории хранится единый lockfile.

## 3. Frontend

### Технологии

- Astro;
- React;
- TypeScript strict mode;
- Tailwind CSS;
- shadcn/ui;
- TanStack Query;
- React Hook Form;
- Zod;
- Lucide Icons.

### Рендеринг

- Публичная оболочка и метаданные формируются Astro.
- Интерактивные части реализуются React islands.
- Публичные данные загружаются из собственного backend.
- Админ-панель является React-приложением внутри Astro-маршрутов.
- Прямые запросы из браузера к Ranked API запрещены.

### Состояние

- Серверное состояние: TanStack Query.
- Локальное состояние выбора: URL-параметры и React state.
- Глобальный state manager в первой версии не нужен.
- Выбранные турнир, дивизион и режим отражаются в URL.

## 4. Backend

### NestJS-модули

#### `AuthModule`

- вход и выход администратора;
- серверные сессии;
- защита административных endpoints;
- rate limiting входа.

#### `TournamentsModule`

- CRUD турниров;
- статусы и переходы;
- публичный каталог;
- блокировка завершённых турниров.

#### `DivisionsModule`

- три доступных типа дивизиона и зафиксированный набор участвующих дивизионов турнира;
- лимиты времени;
- выдача публичных данных дивизиона.

#### `ParticipantsModule`

- локальные профили игроков;
- проверка ника через Ranked API;
- регистрации в дивизионах;
- уникальность участия в турнире.

#### `RankedModule`

- HTTP-клиент Ranked API;
- timeout, retry и обработка 429;
- валидация ответа;
- преобразование внешних данных во внутренний формат.

#### `QualificationModule`

- импорт и повторный импорт;
- определение completed/DNF/missed;
- расчёт размещений, очков и среднего;
- формирование лидерборда;
- выдача сохранённой timeline.

#### `PlayoffsModule`

- создание сетки 4/8/16;
- ручная расстановка;
- ручной счёт;
- ручное перемещение участников;
- опциональный матч за третье место;
- публичное представление сетки.

#### `MediaModule`

- выдача подписанного URL загрузки;
- проверка метаданных;
- привязка обложки.

#### `AuditModule`

- журнал административных действий;
- снимки до/после;
- поиск и просмотр аудита.

## 5. PostgreSQL и Prisma

- Все структурированные данные хранятся в PostgreSQL.
- Prisma является единственным штатным способом записи.
- Сложные агрегаты допускают параметризованные SQL-запросы через Prisma.
- Изменения схемы выполняются только миграциями.
- Денежные данные отсутствуют.
- Времена прохождения хранятся целым числом миллисекунд.
- Даты событий хранятся как `timestamptz` в UTC.
- Исходный Ranked payload хранится в `jsonb`.

## 6. Объектное хранилище

Для обложек используется S3-совместимое хранилище:

- локально — MinIO;
- production — S3, Cloudflare R2 или совместимый сервис.

Frontend не получает постоянный секрет. Backend создаёт ограниченный подписанный URL либо принимает файл и передаёт его в хранилище.

## 7. Импорт Ranked-матча

Последовательность:

1. Администратор вводит `match_id`.
2. Backend проверяет права, статус турнира и уникальность ID.
3. `RankedModule` делает `GET /matches/{match_id}` с timeout.
4. Ответ проверяется схемой.
5. Backend сопоставляет Ranked UUID с регистрациями дивизиона.
6. Незарегистрированные игроки и `spectators` отбрасываются.
7. Для всех регистраций создаётся результат:
   - `COMPLETED`;
   - `DNF`;
   - `MISSED`.
8. Рассчитываются места и очки.
9. В одной транзакции сохраняются:
   - успешно применённая версия импорта;
   - raw payload;
   - нормализованный матч;
   - результаты;
   - timeline;
   - пересчитанные агрегаты регистраций;
   - запись аудита.
10. После commit frontend инвалидирует публичные queries.

При любой ошибке основная транзакция откатывается полностью, поэтому активные публичные данные не меняются. После rollback backend отдельной best-effort записью сохраняет техническую попытку со статусом `FAILED` и безопасным описанием ошибки. Неудача этой диагностической записи не скрывает исходную ошибку от администратора.

## 8. Повторный импорт

- Повторный импорт является полной заменой снимка матча.
- Предыдущая версия не удаляется физически: она сохраняется как история импорта.
- Активной является последняя успешно применённая версия.
- Все места, очки и средние пересчитываются из активных версий всех матчей дивизиона.
- Повторный импорт завершённого турнира требует специального endpoint, причины и подтверждения.

## 9. Кеширование

Первая версия не требует Redis.

- Публичные GET-ответы используют HTTP `ETag` и короткий `Cache-Control`.
- Изображения кешируются CDN/object storage.
- Публичный frontend может кешировать данные TanStack Query 30–60 секунд.
- Админ-панель после записи принудительно инвалидирует соответствующие queries.
- Ranked payload не запрашивается повторно для публичного просмотра.

## 10. Конкурентность

- Сущности, редактируемые администратором, имеют поле `version`.
- Команды изменения передают ожидаемую версию.
- Несовпадение возвращает `409 CONFLICT`.
- Импорт одного матча сериализуется транзакционной блокировкой строки.
- Одновременный импорт разных матчей одного дивизиона допускается только с блокировкой дивизиона на этапе пересчёта.

## 11. Ошибки и наблюдаемость

Backend возвращает единый формат ошибки:

```json
{
  "error": {
    "code": "MATCH_IMPORT_FAILED",
    "message": "Не удалось импортировать матч.",
    "details": {},
    "requestId": "..."
  }
}
```

Логи:

- структурированный JSON;
- `requestId` во всех запросах;
- без паролей, cookie и полного raw payload;
- отдельные события импорта, повторного импорта и изменения сетки.

Минимальные метрики:

- длительность API-запросов;
- количество ошибок по endpoint;
- длительность импорта;
- ответы Ranked API 4xx/5xx/429;
- состояние подключения к PostgreSQL и object storage.

## 12. Версионирование

- API начинается с `/api/v1`.
- Ломающие изменения создают новую версию.
- OpenAPI генерируется NestJS и проверяется в CI.
- Frontend использует контракты из `packages/shared`, но backend остаётся источником истины.
